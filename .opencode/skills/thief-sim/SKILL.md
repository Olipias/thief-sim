# 小偷模拟器 — 项目开发指南

## 项目定位（重要）

* 这是**数位历史（Digital History）专业的 capstone project**，早期 demo 也会作为课程 final project 提交。
* 因此成品必须同时做到两件事：
  1. **是一款真正好玩的游戏**——要像市面上的小偷模拟器一样，有让玩家自愿玩下去的核心循环。不能只是"交作业水平"、只有老师同学会打开一次。
  2. **历史性是立意起点与灵魂**——不是贴皮，而是通过机制融入。核心机制是**文物通灵**（详见下节）。
* 评价标准意识：答辩/提交时，历史系的标准是"史料可信、来源可查、史观端正"；游戏标准是"好玩、上手快、有反馈"。

## 核心历史机制：文物通灵

* 玩家接触文物时，会看到/遇到附着其上的**幽灵**——通常是文物当年的主人、匠人、见证者。
* 幽灵有立场和性格：
  * **帮助玩家**：提供情报（警察位置、密道）、给出任务。
  * **捣乱**：哀嚎/作祟引来警察、制造噪音、干扰视线（已实现雏形）。
  * **讲述历史**：文物背后的真实故事，把"看简介"变成"被讲述"。
* 幽灵台词与故事要**区分史实与演绎**（见"学术规范"）。

## 重点关卡构想：大英博物馆

* 目标：取回近代列强从中国掠夺的文物（如被抢劫、被走私出境的器物）。
* 玩家在撤离后**做选择**：
  * 照常**卖给黑市换钱** → 升级装备，但主线/幽灵态度变化。
  * **归还中国**（交给组织内的"归还线人"/相关渠道）→ 获得特殊事件、幽灵好感、主线推进，但短期收益低。
* 这是"玩法承载历史观点"的样板关卡：选择本身即史观表达。后续任何关卡都可以用同一套"掠夺文物—处置选择"模板。
* 更进一步的关卡包装都可以围绕同一套系统做，不限于大英博物馆（圆明园、敦煌、流失海外的青铜器等主题均可）。

## 可扩展的设计方向（欢迎继续构思更好的）

* **文物档案（图鉴）**：每件文物在游戏内解锁一页"史料卡"——出土地、年代、流失经过、现藏地、参考来源。
* **双故事线**：出售 vs 归还影响组织、幽灵、结局，形成多结局。
* **幽灵任务**：帮幽灵完成遗愿（找到其他被掠夺的部件、送回故乡）解锁能力或剧情。
* **"器物有灵"的视觉语言**：通灵时画面降饱和/夜视色调，警笛声变成历史回响等。

## 学术规范（数位历史专业必做）

* 游戏内出现的真实文物、年代、事件要**可考据**：写明参考来源（博物馆馆藏页、学术论文、档案），在项目文档或游戏内"档案"界面注明。
* 明确标注**演绎部分**（幽灵、超自然元素属于虚构），避免把虚构当史实传播。推荐在开场或档案页放置免责声明。
* 每赛季/版本更新历史内容时同步更新来源清单。

## 技术约定

* 引擎 **Godot 4.7**（`~/.local/bin/godot`），GL Compatibility 渲染，逻辑分辨率 640x360 整数缩放；UI/文案一律中文。
* 目录：`src/autoload`（Game/Audio 单例）、`src/actors`、`src/world`、`src/ui`、`src/levels`（JSON 关卡数据）、`tools`（Python 生成占位美术/音效/地图）、`tests`。
* 占位资源全部由 `tools/*.py` 脚本生成，改素材先改脚本再重新生成，不要手改生成物。
* 保存：`user://save.json`（金币/升级）；自动化测试隔离存档到 `/tmp`。
* 改完代码必须跑测试：
  * `godot --headless --script tests/test_logic.gd`（逻辑单测）
  * `godot --headless res://tests/smoke_test.tscn`（场景集成测试）
  * 两句都要退出码 0；新增功能要补测试。
* 截图检查：`godot --audio-driver Dummy res://tests/screenshot.tscn` → `/tmp/shot_*.png`。
* 本机缺少 libasound/libpulse，游戏会以无声模式运行（正常，不影响逻辑）。

## 维护体系（多 agent 协作）

* 根目录 **AGENTS.md** 是所有 agent 的工作手册（硬性规则、命令、完成定义）。开工前先读它，并从 `docs/ROADMAP.md` 认领任务再动手。
* `tools/verify.sh`：一键全量验证（文档/地图自检 + GDScript 编译检查 + 逻辑单测 + 内容一致性 + 冒烟测试）；收尾必须全绿。
* `docs/ARCHITECTURE.md`：架构地图、数据流、不变量与改造配方；`docs/DECISIONS.md`：决策记录；`docs/SOURCES.md`：史料来源登记。
* 多窗口并行：只改自己任务相关的文件、不整文件重排；改前 `git status` 看并行改动；写完按 AGENTS.md「完成定义」收尾。

## 版本记录流程（强制）

* 每次完成一批改动，必须更新根目录 **CHANGELOG.md**：新版本号（原型期 v0.x.0 为一批功能，v0.x.y 为修复）、日期、变更列表（新增/修改/修复/测试）。
* 同步更新 README.md 的"开发进度"小节。
* 不要用含糊的"优化若干"类描述，要写清改了什么、为什么。
